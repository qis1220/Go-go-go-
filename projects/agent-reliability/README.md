# Agent Reliability｜工具执行状态与可追溯评测

基于睡眠助手与智能床场景提炼的个人原型，聚焦用户从“表达需求”到“功能实际生效”之间的可靠性：分清咨询与操作、功能入口与实际执行、已确认结果与未知状态。

## 业务背景

在睡眠助手产品中，用户既会询问报告和功能，也会通过对话使用智能床或APP服务。例如，睡前打开灯光、进入按摩设置、查看睡眠报告，以及了解某项功能如何使用。

这些请求看起来都是一句话，背后的承接方式却不同：有的需要知识解释，有的只进入页面，有的才会操作设备。主页面对话与全局唤醒的交互条件也不同。产品需要让用户明确知道“下一步在哪里操作”和“操作到底有没有完成”。

本项目从实际产品场景提炼通用问题，使用独立模拟代码验证执行状态；不包含原业务源码、内部接口、设备参数或用户数据。业务场景说明不是线上发布或个人全部职责的证明。

## 用户与核心问题

**终端用户：** 通过睡眠APP和语音入口使用设备及睡眠服务的人。

**原型使用者：** 需要设计、验证Agent功能承接与执行反馈的产品和开发团队。

|业务场景|用户诉求|容易出现的问题|应达到的体验|
|---|---|---|---|
|全局唤醒请求打开灯光|用一句话使用明确功能|将识别到指令或发出请求当成执行成功|可直接执行时，核对结果后反馈；无法确认则说明当前状态|
|主页面请求使用设备功能|找到功能并完成设置|发送消息后直接动作，或把卡片出现当成已开启|先承接到功能卡片与页面，实际操作结果另行确认|
|询问“这个功能有什么作用”|了解功能|因为命中功能名称而触发设备动作|按咨询处理，解释清楚，不执行设备操作|
|请求进入按摩设置|进入可调整参数的页面|页面打开后声称按摩已开始|只确认页面已打开，启动结果取决于后续操作|
|设备未连接或床型不支持|知道为何不能使用及怎么办|给出不能生效的入口，或仍回复成功|明确不可用原因与合理下一步|
|请求发送后超时|知道设备是否已响应|虚报成功，或重试导致重复动作|核对真实状态；无法核对则保留未知|
|请求查看本人或家人报告|获得正确对象的数据解释|把数据查询和设备控制共用同一权限或结果口径|单独处理对象与数据权限，报告可用不等于设备可控|

报告、成员识别与自然语言意图目前用于说明业务边界，尚未在本原型实现。

## 关键产品取舍

1. **区分入口职责。** 主页面可通过卡片和页面承接复杂设置；全局唤醒只在请求明确且能力允许时执行或跳转。需要澄清、依赖历史或混合咨询的请求，交给可持续对话的页面处理。
2. **区分三个结果。** 展示入口、进入页面、设备执行成功分别反馈。不能用“已打开功能”同时表示三种状态。
3. **按功能判断可用条件。** 设备控制依赖绑定、能力和连接；无需设备的APP内容不应因未绑设备被统一拦截。具体还需校验版本和权益。
4. **异常时以可信状态为准。** 执行超时后先核对；无法确认时保留unknown，不能通过更肯定的文案掩盖未知。

## 当前原型验证哪一段

本次MVP只验证上述业务链路中的执行环节：在已经确定要操作后，检查模拟权限与能力、发送前取消、同一操作去重、超时结果和反馈。

|层次|业务需要|当前状态|
|---|---|---|
|意图与入口|区分咨询、使用、否定和模糊表达；决定回答、卡片、跳转或执行|产品设计，未实现自然语言识别和前端|
|设备与权益|判断绑定、床型、连接、版本与权益|仅模拟authorized和supported标志|
|工具执行|成功、失败、未知；去重与发送前取消|已实现离线模拟并验证|
|报告与成员|按对象权限查询和解释数据|不在当前实现范围|
|持续改进|关联轨迹、评估错误、审核经验再接入|已输出模拟轨迹与规则评测；经验仅为draft样例|

## 产品目标

|目标|产品行为|用户价值|
|---|---|---|
|结果可信|区分成功、明确失败和暂未确认，按实际证据反馈|用户知道是否完成，避免根据错误反馈继续操作|
|操作可控|执行前检查权限、功能支持与取消状态；同一操作避免重复发送|减少无效操作与重复执行|
|问题可查|关联消息、请求、执行步骤与结果|团队能定位失败环节，支持修复与回归|

## MVP范围与交互规则

先验证一次操作从请求到结果反馈的完整链路，采用模拟设备，无需模型API或真实硬件。

|场景|处理方式|反馈示例|
|---|---|---|
|确认成功|依据模拟设备结果确认|设备已确认开启|
|明确失败|保留失败状态|设备明确返回执行失败|
|请求超时且能核对结果|查询状态后反馈|核对成功后再告知已开启|
|请求超时且无法核对|保留未知状态，不自动重复发送|暂未确认执行结果|
|同一操作重复请求|复用已记录的结果或未知状态|返回当前状态，不重复发送|
|发送前取消或功能不支持|拦截指令|说明未发送及原因|

权限检查为模拟标志，尚未接入真实身份认证。发送后的取消与撤销不在当前范围。

## 验证方式与产品指标

当前用9个固定模拟用例检查状态、反馈和重复发送行为，结果见下文与 `results/`。

后续真实接入时重点验证：

- **操作结果反馈准确率**：与权威业务状态一致的反馈占比；无法确认时准确表述“未知”也属于正确反馈。
- **重复执行发生率**：同一业务操作被重复执行的比例，需区分传输重试与实际副作用。
- **异常处理完成情况**：失败或未知状态是否有可理解的反馈和明确的下一步。
- **确认耗时**：从用户请求到获得可信结果的耗时，分别统计正常和异常场景。

以上是待验证的产品指标，当前模拟结果不能替代真实用户或设备数据。

## 后续优先级

1. 持久化操作状态，绑定操作ID与参数，验证并发和重启后的去重。
2. 接入真实工具，核对实际状态查询与幂等能力，补充发送后取消的处理。
3. 接入模型理解与表达，分别评测意图、参数、执行和结果反馈。

## 运行

Python 3.10+，无第三方依赖：

```sh
python3 projects/agent-reliability/demo.py
```

在仓库根目录运行。产物位于本目录 `results/`，共9个用例；失败时进程非零退出。

## 执行链路

请求 → 权限 → 发送前取消检查 → 能力校验 → 幂等查询 → 工具发送 → 状态核对 → succeeded / failed / unknown → 明确反馈。

- 模型将来可负责理解表达与提出工具调用；权限、状态、去重由代码执行。本版本不接模型。
- 超时是传输现象，不是业务结论。可核对时以业务状态为准，否则保留unknown。
- message_id描述业务消息；request_id/trace_id记录执行尝试；operation_id代表同一业务操作。重试不能生成新的操作ID绕过去重。
- 轨迹使用自定义JSON结构记录步骤，尚未接入OpenTelemetry。

## 实测结果

9/9个固定模拟用例通过：正常成功、明确失败、执行成功但回执超时、超时未知、发送前取消、不支持、无权限、成功后重复、未知后重复。

验证了该程序在这些设定下的行为，不代表真实Agent成功率100%，也不证明线上业务收益。数据与期望由人设计，生成质量未被测试。

## 失败与经验闭环

假设失败案例：写入后超时，助手却回复“已开启”；用于验证设计，不代表已确认的真实线上故障。修复应先补状态契约及代码校验，再考虑Prompt和经验。见 `experience-candidate.json`，默认draft、禁止运行时发布。通过评测、审核及明确回滚版本后才考虑启用。

后续闭环：轨迹 → 清洗/去重 → 规则与人工检查 → 标注 → 版本化案例集 → 经验假设 → 审核 → 保留集回归。当前只实现模拟轨迹与规则评测，清洗、标注平台、经验检索、MCP发布尚未实现。

## 已知局限

- 内存去重不跨进程、非并发安全；生产需要持久化、原子约束和业务端幂等。
- 同一operation_id要求上游绑定同一操作内容；生产还需验证参数指纹，防止ID复用到不同指令。
- 仅验证发送前取消；发送后取消不保证撤销已执行动作，必须单独查询和设计补偿。
- unknown可能代表动作已执行，也可能未执行。本模拟“不明确状态”没有真实外部环境，不能验证物理状态。
- 明确失败后的人工重试与新操作ID策略未实现。
- 无身份系统、输入Schema、敏感日志治理或网络接口，不作为可部署控制服务。
